# Preprod CI/CD Deployment — Setup Guide

**Version**: 0.1 | **Date**: 2026-08-13 | **Author**: DevOps/DevSecOps + Deployment (Claude Code) | **Status**: Setup instructions for the owner to execute — not executed by this work
**References**: `.github/workflows/deploy-preprod.yml`, `docker-compose.preprod.yml`, `docs/deployment-runbook-moqawil.md`, `.claude/.logs/decisions.md` (2026-08-12 and 2026-08-13 entries)

> **What this is**: a manually-triggered GitHub Actions pipeline that builds Moqawil, pushes an image to GHCR, and deploys it to a cheap VPS over SSH — a one-off test of a real CI/CD deploy, not a launch of the managed-hosting business. That business is still parked pending the AE/CNDP/employment path in the 2026-08-13 decision log entry. This preprod box should never hold real customer data.
>
> **Who runs this**: the owner. Claude Code holds no VPS, DNS, or GHCR-visibility credentials beyond the repo's own `GITHUB_TOKEN`, which the workflow already uses automatically — same blocked-on-owner pattern as `docs/deployment-runbook-moqawil.md`. Everything below is new setup on top of that runbook; steps that don't change (VPS provisioning, backups, uptime monitoring) are linked, not repeated.

---

## 0. Before you start

- [ ] A cheap VPS, separate from any future production box (see §1 for a pick)
- [ ] A subdomain you control for preprod, e.g. `preprod.yourdomain.com` — **not** your real production domain
- [ ] SSH access to that VPS as a user in the `docker` group (see `docs/deployment-runbook-moqawil.md` §3 for Docker install)
- [ ] Repo admin access on GitHub, to create an Environment and add secrets

## 1. Pick a cheap testbed VPS

Per the cost comparison already logged 2026-08-12 (`.claude/.logs/decisions.md`): boutique EU VPS providers run roughly an order of magnitude cheaper than any hyperscaler (AWS/GCP/Azure) for this exact workload (single Docker Compose box — Next.js + Postgres + Caddy), with no horizontal-scaling NFR to design around (`docs/system-design-moqawil.md` §4).

**Recommended for this test**: Hetzner Cloud's smallest shared-vCPU tier (2 vCPU / 4 GB RAM, currently their `CX22` or nearest equivalent) — matches the "Minimum" sizing tier in `docs/deployment-runbook-moqawil.md` §1. Scaleway and OVHcloud are comparable alternatives if you'd rather not use Hetzner. **Verify current pricing/tier names at signup** — this is a fast-moving market and exact SKUs/prices change.

This is a pick for *this pipeline test only*, not a commitment for the eventual managed-hosting tier — that decision still needs its own System Designer pass once that tier is actually scoped (2026-08-12 entry).

## 2. Provision the VPS

Same as `docs/deployment-runbook-moqawil.md` §3 (Docker install) — follow it as-is on the new preprod box. Skip §4 (`docker compose up -d` from a plain checkout) — the pipeline handles first deploy for you once you've done the one-time clone below.

```bash
# On the preprod VPS, once
git clone https://github.com/rhorba/Moqawil.git
cd Moqawil/moqawil
cp .env.example .env
```

Edit `.env` on the VPS with real values (`POSTGRES_PASSWORD`, `AUTH_SECRET` via `openssl rand -hex 32`, `NEXT_PUBLIC_APP_URL=https://preprod.yourdomain.com`, `APP_DOMAIN=preprod.yourdomain.com`) — same guidance as the main runbook §4, just pointed at the preprod subdomain. Leave `E2E_TEST_SECRET` empty, same as always.

**Log in to GHCR from the VPS once**, so `docker compose pull` can fetch the (by default private) image the workflow pushes:
```bash
# A GitHub PAT with read:packages scope, generated by the repo owner
echo "$GHCR_READ_TOKEN" | docker login ghcr.io -u rhorba --password-stdin
```

## 3. DNS

Point an `A` record for `preprod.yourdomain.com` at the VPS's public IP — same mechanics as `docs/deployment-runbook-moqawil.md` §2, different hostname. Wait for propagation before the first deploy, same reasoning (Caddy's ACME challenge needs live DNS).

## 4. GitHub Environment + secrets

`Settings → Environments → New environment → name it "preprod"`. Optionally add required reviewers here if you want a manual approval gate before every deploy runs — not required, but cheap insurance for a pipeline this new.

Add these as **environment secrets** on `preprod` (not repo-wide secrets — keeps them scoped to this one workflow):

| Secret | Value |
|---|---|
| `PREPROD_SSH_PRIVATE_KEY` | Private half of an SSH keypair dedicated to this deploy (don't reuse your personal key — see §6) |
| `PREPROD_SSH_HOST` | The VPS's IP or hostname |
| `PREPROD_SSH_USER` | The SSH user configured in step 2 (in the `docker` group) |
| `PREPROD_APP_DIR` | Absolute path to the cloned repo on the VPS, e.g. `/home/deploy/Moqawil/moqawil` |
| `PREPROD_APP_URL` | `preprod.yourdomain.com` (hostname only, no scheme — the workflow's health check prepends `https://`) |

No GHCR secret needed — the workflow authenticates to GHCR with the repo's built-in `GITHUB_TOKEN`.

## 5. First run

`GitHub → Actions → Deploy Preprod → Run workflow`, leave `ref` as `master` (or point it at whatever branch you're testing), click Run.

Watch the two jobs: `build-and-push` (should take a few minutes, same build the self-host `Dockerfile` already does), then `deploy` (SSHes in, pulls the image, restarts, migrates, health-checks `/api/health` with retries).

## 6. Security notes specific to this pipeline

- The deploy step never passes the `ref` you type into the workflow's manual-trigger form through to any shell command on the runner or the VPS — only into `actions/checkout`'s own parameter, which is safe. Interpolating a user-supplied `workflow_dispatch` input directly into a `run:` shell script is a known GitHub Actions command-injection class (the `${{ }}` text gets substituted before bash parses it); this pipeline avoids it by construction, not by trusting the input. Practical effect: the exact app **version** deployed is controlled precisely by the built image's tag (a computed git short-SHA), while the VPS's checked-out **compose config** always tracks `origin/master` via `git reset --hard` — if you hand-edit any tracked file directly on the VPS, that edit will be discarded on the next deploy (`.env` is gitignored and untouched by this).
- Generate a **dedicated SSH keypair** for this workflow (`ssh-keygen -t ed25519 -f preprod_deploy_key -N ""`), add the public half to the VPS's `~/.ssh/authorized_keys` for the deploy user, and put only the private half in the `PREPROD_SSH_PRIVATE_KEY` secret. If it ever leaks, the blast radius is this one preprod box, not your personal machine's key.
- Restrict that deploy user on the VPS to only what it needs (Docker group membership + write access to `PREPROD_APP_DIR`) — don't reuse an SSH key that also has broader `sudo` access elsewhere.
- The GHCR image defaults to **private** (inherits repo visibility) — the VPS's one-time `docker login` in §2 is what lets it pull. Don't flip the package to public unless you have a specific reason to.
- This box should never receive real tenant/client PII — it's a pipeline test environment. If you later want to point a pentest at a "staging-like" box per `docs/pentest-scope-moqawil.md`, that's a separate, deliberate decision, not an automatic consequence of this pipeline existing.

This doc only covers what's different for a CI/CD-deployed, GHCR-image-based box instead of a manually-`git pull`led one.
