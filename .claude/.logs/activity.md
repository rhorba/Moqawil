### 2026-08-11 BUGFIX — Walkthrough video only showed the browser window's top-left corner (post-push, caught by user watching the recording)
- **Specialist**: DevOps/DevSecOps
- **Summary**: After Sprint 10's push, the user reported the recorded video showed only the top-left corner of the app, not the full browser window (screenshots were unaffected). Root cause: this machine runs Windows display scaling at 150% (native 1920x1080, logical 1280x720 — confirmed via `AppliedDPI` registry value 144). `scripts/run-walkthrough.mjs`'s ffmpeg `gdigrab` capture is a fixed 1280x720 **physical**-pixel region, but Chromium's `--window-size=1200,700` launch arg is interpreted in logical (DIP) pixels and was rendering at ~1.5x that in physical pixels (~1800x1050) — far larger than the capture region, so only the window's top-left corner ever fell inside the recorded frame. Fixed by adding `--force-device-scale-factor=1` to `playwright.walkthrough.config.ts`'s launch args, forcing a 1:1 physical:logical pixel mapping so the window's actual size matches its requested size regardless of OS scaling. Verified by extracting frames from the re-recorded video at 20s/70s/85s — full window (address bar + full app content) visible throughout. Separately, re-running the walkthrough surfaced a second issue: the production server (still running from an earlier `next start`) had gone stale after a `rm -rf .next && pnpm build` was run against the same directory mid-session for the coverage/build verification gate — a recurrence of this project's known Windows/OneDrive `.next`-corruption issue — causing a real client-side JS chunk-load exception during the first re-recording attempt. Restarted the production server cleanly on the already-fresh build; confirmed via a clean dry-run before re-recording for real.
- **Status**: resolved — new video `walkthrough-2026-08-11T04-56-11.mp4` (94.6s) replaces the broken one; screenshots (unaffected, but naturally regenerated by the same test run) refreshed to match.
