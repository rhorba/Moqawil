### 2026-08-11 BUG — `getClientAnnualTotal` had no ownership boundary of its own (IDOR defense-in-depth gap)
- **Specialist**: Security Engineer (Sprint 11 IDOR re-audit, elevated to CRITICAL priority for the multi-tenant hosted deployment — see `docs/security-moqawil.md` §1/§2)
- **Summary**: Full audit of every function in `apps/web/src/lib/queries/*.ts`, every server action, and every PDF/UBL API route for missing `entrepreneurId`/ownership filters. One gap found: `getClientAnnualTotal(clientId, year)` in `client.ts` queried `invoices` filtered only by `clientId` + `fiscalYear`, with no `entrepreneurId` check — the one function in the codebase that broke the two-argument ownership-check pattern every other query follows (e.g. `getClientById(clientId, entrepreneurId)`). Not currently exploitable: all 5 call sites (`clients/[id]/page.tsx`, `invoices/[id]/page.tsx`, `invoices/actions.ts` ×2, `quotes/actions.ts`) already verify the client's ownership via a prior `getClientById`/entrepreneur-scoped fetch before calling it. But it was a latent landmine relying entirely on every current *and future* caller remembering that precondition — exactly the kind of gap that matters once "many strangers' data in one DB" replaces "one operator, one instance" as the threat model.
- **Fix**: `getClientAnnualTotal` now takes `entrepreneurId` as a required parameter and filters the query by it directly (`client.ts`), matching every other function's pattern. Updated all 5 call sites + 5 test call sites across `client-db-integration.test.ts` and `quote-db-integration.test.ts`. Added a new regression test: `getClientAnnualTotal returns zero for a client requested under a different entrepreneur (IDOR guard, Sprint 11)`.
- **Also found while re-auditing** (not a bug, logged for completeness): a stale Playwright e2e fixture row (`accountant-dashboard.spec.ts`'s `e2e-accountant-ae@moqawil.test`, ICE `000000000000009`) collided with `quote-db-integration.test.ts`'s hardcoded fixture ICE constant on the `entrepreneurs.ice` unique constraint, silently no-op'ing that test's entrepreneur insert via `onConflictDoNothing()` and cascading into an FK-violation failure on the client insert. Cleaned up the stale row to unblock this session; the underlying fixture-value collision between the Playwright and Vitest test suites is pre-existing (not introduced this sprint) and not fixed here — worth a future small housekeeping task to give each test suite's hardcoded fixture ICE/email values non-overlapping ranges.
- **Everywhere else audited** (`invoice.ts`, `quote.ts`, `declaration.ts`, `entrepreneur.ts`, `accountant.ts`, all 7 `actions.ts` files, all 4 PDF/UBL API routes): ownership filtering already correct and consistent. `getPendingInviteByToken`/`acceptAccountantInvite` correctly use the capability-token pattern (unguessable 256-bit token + status/expiry/email re-check at write time) rather than an entrepreneurId filter, which is the right pattern for a cross-tenant grant mechanism.
- **Status**: FIXED same session, verified via `pnpm --filter @moqawil/web typecheck` (clean) and both affected test files (16/16 passing).
- **Impact**: medium (not currently exploitable, but closes a real defense-in-depth gap ahead of the Sprint 11 multi-tenant hosted launch).

### 2026-08-11 BUG — Recurring ICE fixture collisions between Vitest DB-integration suites and Playwright e2e/walkthrough specs (root-caused and fixed)
- **Specialist**: Tester, on direct user instruction ("fix the ICE fixture collision properly across test suites") after the same class of bug was hit and manually patched 3 times this session (once flagged in the entry above, twice more during Sprint 11 verification) and once previously in Sprint 10 (commit `f024466`).
- **Root cause (two compounding bugs)**:
  1. All `*-db-integration.test.ts` Vitest files and all Playwright e2e/walkthrough specs write directly to the one shared, persistent local dev Postgres instance, and none of them wipe their rows after a successful run. Different suites had independently picked low, overlapping hardcoded 15-digit ICE constants (`000000000000001` through `...011`), so two unrelated suites eventually claimed the same `entrepreneurs.ice` value.
  2. `entrepreneurs.ice` is UNIQUE, and every fixture insert used bare `.onConflictDoNothing()` with no `target` column — Drizzle/Postgres treats that as "ignore ANY conflict," so a real ICE collision silently no-op'd the insert instead of throwing. The entrepreneur row the test expected to exist was never created, and the failure only surfaced downstream as a confusing FK-violation error on a later insert (e.g. the client or invoice row), far from the actual cause.
- **Fix**:
  1. Assigned every DB-touching suite a reserved, non-overlapping ICE block (documented in `docs/test-strategy-moqawil.md` §7, "Fixture ICE Numbering Convention" — table of file → block). Renumbered all fixture ICE values across 7 Vitest files (`accountant-`, `client-`, `declaration-`, `entrepreneur-`, `invoice-queries-db-integration.test.ts`, `invoice-numbering.test.ts`, `quote-db-integration.test.ts`) and 3 Playwright specs (`e2e/happy-path.spec.ts`, `e2e/accountant-dashboard.spec.ts`, `walkthrough-e2e/walkthrough.spec.ts`). `pdf-templates.test.ts` excluded on purpose — confirmed by reading it in full that it never touches the database (calls the PDF renderers directly with in-memory objects), so its reused ICE `000000000000001` poses no collision risk.
  2. Every `entrepreneurs`/`users` fixture insert's `.onConflictDoNothing()` across all 8 DB-touching Vitest files now specifies an explicit `{ target: entrepreneursTable.id }` / `{ target: usersTable.id }`, so a future real collision throws a loud, immediate unique-constraint error at the point of insertion instead of silently vanishing and surfacing as an unrelated FK error later.
  3. Separately found and fixed while verifying: `apps/web/vitest.config.ts` had no `fileParallelism` setting, so Vitest's default (run test files concurrently) let these same DB-integration files race each other on the shared Postgres instance — confirmed via isolation reruns that every file passes 100% alone but intermittently fails (wrong row counts/sums) only under concurrent file execution. Set `fileParallelism: false`; suite is only 14 files so the sequential cost is a few seconds, and it removes a second, structurally different source of the exact same "confusing, hard-to-diagnose DB test failure" symptom this task was about eliminating.
- **Verification**: `pnpm --filter @moqawil/web typecheck` clean. Full Vitest suite (`pnpm test`, all 14 files / 124 tests) green on 2 consecutive runs. Full Playwright suite (`pnpm exec playwright test --workers=1`, matching `playwright.config.ts`'s actual CI setting) green, 21/21 non-skipped tests, on a freshly rebuilt `.next` cache. (A local-only run with Playwright's auto-detected 4 workers showed 3 failures from genuine cross-spec/cross-worker contention on the one shared dev server + DB — not reproducible under CI's real `workers: 1` config, and unrelated to ICE data: no unique-constraint or FK errors in that run, just page-load timing.)
- **Status**: FIXED.
- **Impact**: medium — this was pure-friction technical debt (wasted diagnosis time, manual DB cleanup 4 times across 2 sprints), not a production risk, but it was actively eroding trust in the test suite's failures being real.
